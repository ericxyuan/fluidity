# Reconciliation decisions

These decisions explain the integrated runtime rules; they are not competing skill
instructions. Exact source files and retained/rejected mechanisms are in source-map.json.

| Difference and reason | Fluidity decision | Authoritative output |
| --- | --- | --- |
| Design's strict under-300ms advice coexists with 400ms Sonner and 500ms drawer examples | Short ordinary UI timing; preserve justified longer travel or library tuning; physics settling is not a fixed duration | motion-policy.md |
| Design's default no-bounce Apple material differs from playful source spring demos | No ordinary overshoot; gesture momentum may justify restrained bounce | motion-policy.md, gesture-mechanics.md |
| Design direct manipulation is 1:1, but decorative mouse tracking uses spring lag | Follow the finger for controls; spring lag is optional for decoration only | gesture-mechanics.md |
| Motion Patterns uses shorthand/layout springs while Design prefers full transform strings under load | Keep necessary dynamic/layout mechanisms; use CSS/WAAPI for fixed transitions and profile driver/compositor separately | motion-policy.md |
| Source performance rules broadly ban height, while accordions and Composition expandable measure it | Allow isolated short height reflow for disclosure; observe live content, prevent feedback loops | recipes.md, measured-disclosure.tsx |
| Design materialization suggests animated blur; Composition distorted glass adds fractal filters | Keep readable static bounded material, solid preference fallback, optional opacity/scale arrival; reject distortion by default | extensions.md, fluidity.css |
| Motion morphing overlays and Application dialog-stack prioritize visual identity over complete modal behavior | Retain stable shared IDs/context layering; use host native/Radix/Base UI focus, Escape, isolation and restoration | source component references |
| Motion unmounting disclosure versus Composition persistent expandable | Retain both only because state lifetime differs; one simple API, one compound persistent draft API | selection-and-integration.md |
| Composition sortable list changes order; Application card-swipe changes selection; list/dialog stacks imply different tasks | Stacked Card Set is bounded selection only, with handle drag and native alternatives; no reorder or modal inference | extensions.md, stack-model.ts |
| Application/Composition selectors expose rich visuals but uneven semantics | Keep state/layout mechanisms; native or existing headless controls own semantics; one primitive family per host | application.md, composition-patterns.md |
| Source demos use global layout IDs, fixed widths, timers and animation input locks | Scope IDs, adapt width/content, clean up observers, make state immediate, permit reversal and hide stale focus targets | local adapters |
| Source animation review and prototype skills impose report formats, refusal/approval stages, promotional replies and fixed chrome | Preserve evidence-based judgment and scoped comparison; follow actual user authorization through implementation | Core and Review skills |
| Application source skill requires runtime remote catalog lookup | Local detailed recipes/adapters replace that lookup; clones and mapping stay build-time only | Components skill |
| Catalog abundance conflicts with simple task needs | Purpose, hierarchy, host conventions and accessibility select components; reject decoration and duplicate variants | Core and selection-and-integration.md |

Viewing Importance, Apple Glass Card, Stacked Card Set and orchestration are explicitly
versioned conservative extensions authorized by the user. They integrate the sources
above and make no claim to satisfy additional unseen feature specifications.
